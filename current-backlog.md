## 5. Architectural gaps

5.2. **No `Freezable` / immutability.** Useful for shareable value-type-like Models (Brushes, Geometries).

5.9. **Command infrastructure is one layer deep — WPF has five.** Today we ship `ICommand` ([src/runtime/command.ts](src/runtime/command.ts)) + `RelayCommand` + `Button.Command` / `Button.CommandParameter` DPs (with the active command's `CanExecuteChanged` auto-disabling the button) + the `InvokeCommandAction` trigger action (so `on Click { InvokeCommand[Command=$SaveCommand] }` reads a command off DataContext and fires it). That's the *MVVM-first* slice: one VM property exposed as `ICommand`, one control bound to it.

  WPF's surface is meaningfully larger. Five distinct gaps, roughly in order of payoff:

  - **5.9.1 — `ICommandSource` contract + `CommandTarget`.** WPF defines a shared contract (`Command`, `CommandParameter`, `CommandTarget`) for controls that invoke commands. Promote the Button-specific DPs onto a base or mixin and pick up `MenuItem`, `Hyperlink`, `ToggleButton`, anything else that shouts "click → invoke". The genuinely new piece vs. today is `CommandTarget` — a `Visual` DP that overrides the routed-command target from "the currently-focused element" to a named one. Loadbearing only once `RoutedCommand` exists (5.9.3); without it `CommandTarget` is dead weight. Plain ICommand-as-VM-property stays exactly as today (the DP just sits at `undefined`). Cheap, additive, no new concepts.

  - **5.9.2 — `InputBindings` + `KeyBinding` / `MouseBinding`.** Per-Visual collection of gesture-to-command mappings declared in markup: `InputBindings { KeyBinding[Key=S, Modifiers=Control, Command=$SaveCommand] }`. Today there's no way for a `.mu` author to say "Ctrl+S fires this command" without writing `on KeyDown { … }` handler glue. Slots cleanly into the existing routed-event pipeline — bindings live on the Visual, a `PreviewKeyDown` listener at the focus root matches gestures top-down and invokes the matched command's `Execute(CommandParameter)`. Highest *user-facing* payoff because keyboard shortcuts are universally expected and the framework currently has none. Needs a focus-management story for "which Visual's InputBindings get consulted" (typically: the focused element first, then walk up).

  - **5.9.3 — `RoutedCommand` + `CommandBindings`.** WPF's bigger architectural commitment. `RoutedCommand` is a singleton command identity (`ApplicationCommands.Save`); execution doesn't happen on the command itself but bubbles through the visual tree via the routed-event system. Each Visual carries a `CommandBindings` collection of `(command, executed, canExecute)` triples; the routing walks from the focused element up looking for the first matching binding. Decouples command identity from VM ownership — a TextBox can fire `ApplicationCommands.Copy` and ANY ancestor in scope handles it. Loadbearing for the named-command library (5.9.4) and for cross-tree command routing. Requires the focus integration above plus a `CommandManager.Execute(command, parameter, target)` entry point. For an MVVM-first framework where commands are usually per-VM RelayCommands, this is less essential than in classic WinForms — its real win is *app-wide* commands shared across views (Save / Cut / Copy / Paste / Find). Separate decision driven by whether a real demo needs cross-tree routing.

  - **5.9.4 — Named-command libraries: `ApplicationCommands` / `EditingCommands` / `NavigationCommands` / `MediaCommands`.** Static identity-only `RoutedCommand` singletons that controls wire up internally. `TextBox` registers internal `CommandBindings` for the editing commands (Cut, Copy, Paste, SelectAll, …); a menu item or button referencing `EditingCommands.Copy` then automatically routes to whatever TextBox has focus. Trivial implementation once 5.9.3 lands — the value is the *integration* (existing controls have to opt in). Without 5.9.3 these are just names.

  - **5.9.5 — `CommandManager.RequerySuggested`.** Centralized periodic + focus-change-driven `CanExecuteChanged` synthesis. WPF fires `RequerySuggested` whenever focus moves, a property changes that might affect a command, etc.; commands without explicit `RaiseCanExecuteChanged` still update their consumer chrome. `RelayCommand` already covers the common case (VM calls `RaiseCanExecuteChanged` explicitly), so this is the lowest-priority item. Useful for `RoutedCommand`s whose `CanExecute` depends on focused-element state.

  **Recommended cut line.** 5.9.1 + 5.9.2 first (broad payoff, no new architecture — the existing routed-event + ICommand machinery is enough). 5.9.3 + 5.9.4 + 5.9.5 treated as a separate decision once a demo demonstrates the cross-tree routing need (typical trigger: a real menubar with shared edit commands, or an app-shell shortcut palette).

5.7. **`mural-hit` pad opt-out for non-interactive Visuals.** Today `SvgRenderer` emits an invisible `<rect class="mural-hit" fill="none" pointer-events="all" .../>` inside every Visual's outer `<g>`, sized to its `ArrangedRect`. The pad exists so pointer events register on the whitespace between painted descendants (a TreeView row's gaps between chevron and label glyphs would otherwise fall through under SVG's default `visiblePainted`). One pad per Visual ≈ half the `<rect>` count in any non-trivial scene (~280 of the 633 rects in the tree-view demo, ~28 KB of attributes for a 108 KB dump). For most Visuals the pad is dead weight — purely decorative `TextBlock`s, `Border`s, layout panels, etc. never get a routed-event listener and never appear in an `IsMouseOver`/`IsPressed`/`IsFocused` trigger. The pad is only load-bearing for Visuals that: (a) have a per-instance routed-event listener (`AddPointerDownListener` etc.), (b) appear as the watched target in a `PropertyTrigger` over `IsMouseOver`/`IsPressed`/`IsFocused`, (c) have `Focusable=true`, or (d) override an input virtual (`OnPointerDown`, …). The renderer doesn't currently know any of those criteria. Two viable shapes for the opt-out: an `interactive` bit on Visual that subclasses opt into (cheap, explicit, requires touching every interactive control); or a renderer-side derivation that walks the listener Maps + Style triggers when materializing the outer `<g>` (no control-side change, but couples the renderer to the routed-event + style internals). Either way, the pad still gets re-emitted at the moment a Visual transitions from non-interactive to interactive (new listener added at runtime, Focusable flipped, a trigger installed via Style.OverrideMetadata on a descendant class). Pairs naturally with the existing "lazy-attach `mural-own`" optimization — together they could plausibly halve the steady-state SVG size for layout-heavy demos.

## 8. Drag & drop (v2 follow-ups)

The v1 design (`docs/superpowers/specs/2026-06-04-drag-and-drop-design.md`) lands a WPF-parity routed-event drag/drop subsystem — `AllowDrop` / `IsDragOver` DPs, `DragEnter`/`Over`/`Leave`/`Drop` routed events, `DataObject` formats map, `DragDropEffects`, imperative `DragDrop.DoDragDrop` + declarative `IsDraggable` / `OnDragStart` sugar, and three preview modes (framework ghost / null / DataTemplate). These items are intentionally out of scope for v1 and are listed here as concrete follow-ups so the design isn't load-bearing for them.

8.2. **Multi-pointer drags.** v1 assumes one drag session at a time; a second `pointerdown` during a session is ignored. Lifting this means promoting `_dragSession` from `DragSession | null` to a `Map<pointerId, DragSession>` and tracking per-pointer cursor state. Useful for touch/pen multi-finger composition scenarios; not worth the bookkeeping until a concrete demo asks for it.
