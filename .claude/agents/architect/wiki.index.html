Architect Agent

A starter project that turns Claude Code into an architecture-modelling assistant. Author models in YAML, get diagrams as SVG, ship a single-file viewer.

What this is

This template gives you a project folder with two things baked in:

  1. An architect agent for Claude Code that knows the meta-models, the file conventions, and the build pipeline. Invoke it with slash commands or just describe what you want.
  2. A vendored toolchain — Python engines, ADL spec, visual libraries — that compiles your YAML models into validated SVG diagrams and bundles them into a self-contained HTML viewer.

You write models. The agent scaffolds files, validates against the spec, runs the build, and shows you the output. Two meta-models ship today: enterprise-architecture (locations, blocks, components, scenarios) and BPMN (pools, lanes, tasks, gateways, flows).

Quick start

  1. Clone the template (or click Use this template on GitHub).
  2. Open the folder in Claude Code. The architect agent and slash commands are auto-discovered from .claude/.
  3. Set up the project name: 
    /setup-project my-architecture
    The descriptor file gets renamed, its id/title updated, and the VS Code .view syntax-highlighting extension is registered. Rename the parent folder to match if you care about the convention default (the orchestrator looks for <dir-name>.proj.yaml).
  4. Author your first model. Either use the agent (“create a BPMN model for order fulfilment”) or run a slash command. The agent fills models/<id>/, registers the model in the descriptor, and adds a default view.
  5. Build. The agent runs the toolchain and shows you the output path; open the SVG in your browser or run a --release build for the bundled viewer.

Pre-requisite: Python 3.10+ on your machine. Nothing else — no pip, no npm, no global installs. The toolchain is vendored.

The architect agent

What it does

The architect agent ships at .claude/agents/architect.md. It’s a domain expert in the framework's meta-models and toolchain. Its responsibilities:

  • Author models, views, and library entries — translates your intent into the right files in the right places.
  • Validate by running the compilers; the compilers are the validators (a clean exit means the model is spec-valid).
  • Debug compile errors — reads the compiler source if needed (it’s right there under .claude/agents/architect/).
  • Build diagrams and the viewer bundle.

You delegate to it explicitly via slash commands or by describing a task involving models, views, scenarios, BPMN processes, or anything in .claude/agents/architect/{adl,visual_libraries,technology_library}/. For unrelated work (general coding, prose), the main Claude session handles it.

Hard rules

The agent follows non-negotiable rules carried over from the toolchain’s author preferences. Knowing them helps you predict what it will and won’t do:

  • Won’t invent test inputs. If the agent needs a sample model to verify something, it asks you first instead of fabricating one.
  • Purpose-first component naming. A component is named after what it does (language-model), not what it’s built with (azure-openai-gpt4o). The technology link goes through implemented-by. Three relationship types only: Interaction (default connector), Enablement (enabled-by), Hosting (hosted-by).
  • Globally unique ids within a model. Actor, block, location, and component ids share a single namespace inside one model.
  • Author owns connector routing for architecture views. The renderer doesn’t auto-route; you express paths explicitly with -->, -|, etc. (BPMN auto-layout is the exception — that’s template-driven.)
  • margin shrinks bounds; padding doesn’t.
  • No cross-references to TOGAF, ArchiMate, C4. Stay within the meta-models defined under adl/.

Meta-models

A meta-model is the schema your model conforms to. The descriptor declares which meta-model each model uses, and the toolchain dispatches to the right compiler/renderer.

Meta-modelSource extensionFor modelling
enterprise-architecture.arch.yamlEnterprise architectures — locations, actors, blocks, components, scenarios, connectors.
bpmn.bpmn.yamlBusiness processes — pools, lanes, tasks, events, gateways, sequence/message flows.

Enterprise architecture

Models a system as actors initiating scenarios that trace through components grouped by location. The shape of an .arch.yaml:

meta:
  id:         my-arch
  title:      My Architecture
  meta-model: enterprise-architecture

imports:
  - default              # technology library

locations:
  azure: { label: Azure, type: cloud/paas }

actors:
  business-user: { label: Business User, type: internal }

scenarios:
  conversational:
    label: Conversational
    outcome: Grounded response
    sequences:
      - sequence:
          Title: User-initiated chat
          Entry Point: business-user
          steps:
            - business-user → chat-surface
            - chat-surface  → agent-orchestrator

blocks:
  chat-surface:
    label: Chat Surface
    in: m365
    components:
      - id: teams-chat
        label: Microsoft Teams
        category: ai-chat
        implemented-by: [microsoft-teams]

components:
  azure:
    - id: language-model
      label: Language Model
      category: foundation-model
      implemented-by: [azure-openai-gpt4o]

connectors:
  - from: business-agent
    to:   agent-orchestrator
    type: enabled-by
  - business-agent calls workflow-engine     # short form (Interaction)
  - - autonomous-agent                       # tuple form
    - agent-orchestrator

Validator rules the compiler enforces: a component’s category must be in its implementing technology’s applicable-to; a component’s location must intersect the technology’s available-in; connector endpoints must resolve; imports must exist.

BPMN

Models a business process as flow nodes (tasks, events, gateways) on swimlanes (pools containing lanes), connected by sequence flows within a pool and message flows between pools. The shape of a .bpmn.yaml:

meta:
  id:         my-process
  title:      My Process
  meta-model: bpmn

pools:
  customer:
    label: Customer
    lanes:
      self:
        label: Customer
        flow-nodes: [start-shopping, checkout, order-placed]
  seller:
    label: Seller
    lanes:
      sales:
        label: Sales
        flow-nodes: [receive-order, validate-payment, ship]

events:
  start-shopping:  { event-type: start }
  order-placed:    { event-type: end }
  receive-order:   { event-type: start, trigger: message }

tasks:
  checkout:         { label: Checkout, type: user }
  validate-payment: { label: Validate Payment, type: service }
  ship:             { label: Ship Order, type: send }

gateways:
  payment-gate:
    type: exclusive
    default: rejected-flow

flows:
  - { from: start-shopping, to: checkout,        type: sequence }
  - { from: checkout,       to: receive-order,   type: message, label: "Place Order" }
  - { from: receive-order,  to: validate-payment, type: sequence }

Validator rules: sequence flows stay within a single pool; message flows cross pool boundaries; at least one start event; every node has a path to an end event.

Views

A view is a rendered diagram of a model. Two authoring modes — mutually exclusive:

Source-driven

You author the layout in the .view DSL — a TikZ-flavoured language with explicit panel layout (vstack, hstack, ugrid) and twelve connector operators (-->, -|, -,, etc.). This is the typical mode for architecture views, where layout intent is aesthetic and per-architecture.

import visual-library     Default
import technology-library default

view $my-arch [
    title       = "My Architecture"
    background  = "#FAFAF9"
    padding     = 20
]
{
    vstack {
        $business-user
        $chat-surface vstack { ... }
    }
    connectors {
        $business-user --> $chat-surface
    }
}

Template-driven

The view declares a model-template: — a registered generator builds the whole diagram from the model alone. The .view file’s body stays empty. This is the typical mode for BPMN, where layout is mechanical (swimlane bands, topological placement, orthogonal connectors) and a generator does the work.

import visual-library BPMN

view $my-process [
    title          = "My Process"
    background     = "#FAFAF9"
    model-template = auto-layout
]
{
}

Today the only registered template is auto-layout for the BPMN meta-model.

Building & viewing

From the project root:

# Full build — every model, every view → output/debug/
python .claude/agents/architect/toolchain/build.py .

# Release build — also produces a self-contained architecture-viewer.html
python .claude/agents/architect/toolchain/build.py . --release

# Single view — fast iteration, skips manifest + sequence diagrams
python .claude/agents/architect/toolchain/build.py . --view <model>/<view>

# Single view in multiple formats
python .claude/agents/architect/toolchain/build.py . --view m/v --format svg --format drawio

The architect agent runs these for you when you say “build” or invoke /build. The compilers are the validators — a clean exit means the model is spec-valid.

Output structure

output/
└── debug/                                 (or release/)
    ├── viewer-manifest.json               ← what the viewer loads
    ├── architecture-viewer.html           ← only in --release
    └── <model-id>/
        ├── <model-id>.{arch,bpmn}.compiled.yaml
        └── views/
            └── <view-id>/
                └── <view-id>.svg

The viewer

Two ways to view:

  • Direct SVG. Open any output/debug/<model>/views/<view>/<view>.svg in your browser.
  • Bundled viewer. Run a release build and open output/release/architecture-viewer.html. It contains the full manifest plus every diagram inlined as SVG, so it works under file:// with no server, no fetches. Side-by-side model picker, view list, sequence-diagram pane (for architecture models), zoom + pan + scenario filtering.

Customising

Custom technologies

Add project-local technology entries inline in your .arch.yaml under custom-technologies:. Use this for company-specific services or one-off integrations that aren’t reusable across architectures.

custom-technologies:
  custom-validator-svc:
    label: Request Validator
    icon: .claude/agents/architect/technology_library/default/resources/api-service.svg
    available-in:  [azure]                  # which locations it can run in
    applicable-to: [service]                # which categories it can fill

Adding a custom technology library

Create .claude/agents/architect/technology_library/<your-lib>/index.yaml with categories and technologies, drop icons under resources/, and import it in the model:

imports:
  - default
  - your-lib

Custom views

Architecture views are hand-authored in the .view DSL. Read the visual-engine wiki at .claude/agents/architect/visual_engine/wiki/ for the full primitive set: layout panels, anchor placement, connector operators, channel-aware routing.

Troubleshooting

The viewer is blank in the browser

Two common causes:

  • Debug build, opened from file://. The debug build relies on fetch() to load the manifest, which browsers block under file://. Either run a --release build (which inlines everything) or serve the dev viewer over HTTP: from the project root, python -m http.server 8765 then open http://localhost:8765/.claude/agents/architect/architecture-viewer/.
  • Empty manifest. If you have zero models, the viewer shows an empty state. Add at least one model.

Compile error: meta-model mismatch

The descriptor declares one meta-model but the source file declares another (or vice versa). Reconcile the two: the source file’s meta.meta-model: and the descriptor entry’s meta-model: must agree.

Compile error: technology ‘X’ not applicable to category ‘Y’

The component declares a category the technology can’t fill. Either change the component’s category, or add the category to the technology’s applicable-to, or pick a different technology in implemented-by.

Compile error: location not in technology’s available-in

Same shape: the component is in a location the technology can’t run in. Same three fixes — change the component’s in:, broaden the technology’s available-in:, or pick a different technology.

Disk-write truncation

Files written via the agent very rarely end up truncated at the tail or with NUL bytes inserted. Suspected antivirus or sync-indexer interaction. If you see YAMLError: end of stream or strange parser failures, run the integrity check:

python .claude/agents/architect/visual_engine/check_integrity.py

Three relationship types (architecture)

  • Interaction — A talks to B at runtime. Default connector. Authored as {from: A, to: B} or short forms.
  • Enablement (enabled-by) — A is enabled by B. B is a capability A relies on but doesn’t directly call (auth, identity, networking).
  • Hosting (hosted-by) — A runs on B. B is the platform/environment that contains A.

BPMN flow types

  • Sequence flow — within a single pool. Solid arrow.
  • Message flow — between pools. Dashed arrow with open arrowhead.
