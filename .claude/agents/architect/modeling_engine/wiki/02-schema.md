# 02 — Schema & syntax

The shape of an architecture description file. Refers to the meta-model concepts in [01](01-meta-model.md).

## Top-level structure

```yaml
meta:               { id, title }
locations:          { <id>: { label, type, parent? }, … }
actors:             { <id>: { label, type }, … }
imports:            [<library-name>, …]
categories:         { <id>: { icon }, … }    # inline overrides for imported categories
custom-technologies: { <id>: { … }, … }      # architecture-specific tech (custom services)
scenarios:          { <id>: { label, outcome, sequences: [...] }, … }
blocks:             { <id>: { label, in, components: [ <component>, … ] } }
components:
  <location>:       [ <component>, … ]       # list of objects, each with explicit `id:`
connectors:         [ <connector entry>, … ]
```

`components:` is grouped by location — the YAML key under `components:` is the location name. The grouping is organisational only; component IDs are globally unique (see [01](01-meta-model.md)).

## Component fields

| Field | Type | Notes |
|---|---|---|
| `id` | string | Identifier — globally unique. Required in list form (or autogenerated from `label` + `category`). Required as the YAML key in dict form. |
| `label` | string \| list | Required. Display name on the diagram. List form represents a multi-line label. |
| `category` | string | Required. References a category from the resolved registry. |
| `implemented-by` | list of string | List of technology IDs. Must resolve to entries in the technologies registry. |

Anything else — what hosts this component, what enables it, what it consumes, what it's available through, what it calls — lives in the `connectors:` block as typed edges. See [01 — Meta-model](01-meta-model.md) for the rationale.

## Component authoring — list form (primary)

```yaml
components:
  power-platform:
    - id: business-agent              # explicit id
      label: [AI, Agent]
      category: ai-agent
      implemented-by: [copilot-agent]
    - label: [Agent, Orchestrator]    # id auto-generated → "agent-orchestrator"
      category: orchestration-engine
      implemented-by: [copilot-studio]
```

This is the form the compiler emits, the architecture source uses, and authors should default to. `id:` is always visible (explicit or autogenerated).

The autogen rule combines **`label` + `category`**: both contribute parts (lowercased, non-alphanumeric runs become hyphens), then duplicate parts are removed in order:

| Label | Category | Autogenerated id |
|---|---|---|
| `[AI, Agent]` | `ai-agent` | `ai-agent` *(label parts already cover the category)* |
| `[Microsoft, Teams]` | `ai-chat` | `microsoft-teams-ai-chat` |
| `Database` | `database` | `database` |
| `[Workflow, Engine]` | `service` | `workflow-engine-service` |
| `[Knowledge, Index]` | `semantic-index` | `knowledge-index-semantic` *(`index` already in label parts)* |
| `[Platform, API]` | `platform-api` | `platform-api` |

If autogen would collide with an existing id, the compiler errors. Provide an explicit `id:` to disambiguate.

## Component authoring — dict form (legacy/compact alternative)

The compiler also accepts dict form, where the YAML key is the id:

```yaml
components:
  power-platform:
    business-agent:
      label: [AI, Agent]
      category: ai-agent
      implemented-by: [copilot-agent]
```

No autogen — the YAML key is always specified. More compact for small models. The compiler internally normalises both forms to the same representation.

## Scenarios — sequences and steps

A scenario carries a `label`, an optional `outcome`, and one or more **sequences**. Each sequence is a single named flow with its own entry point and ordered step list. A scenario may carry several sequences when the same business outcome can be reached through different entry points (e.g. user-initiated vs. agent-initiated variants of the same conversation).

```yaml
scenarios:
  conversational:
    label: Conversational
    outcome: Grounded, permission-scoped response
    sequences:
      - sequence:
          Title: User-Initiated Conversation with AI Agent
          Entry Point: business-user
          steps:
            - business-user        → chat-surface              # calls (default)
            - chat-surface         → business-agent
            - agent-orchestrator   →[consumes] knowledge-index
            - external-ai-agent    →[event] command-bus
```

### Sequence fields

| Field | Required | Notes |
|---|---|---|
| `Title` | yes | Human-readable name of the sequence. Used to derive a `sequence` slug surfaced on each emitted connector. |
| `Entry Point` | yes | Bare id of the actor, component, or block that initiates this sequence. Validated against the global namespace. |
| `steps` | yes | Ordered list of `<src> → <dst>` strings. Same grammar as before. |

The wrapper key `sequence:` may be omitted — both `- sequence: { Title, Entry Point, steps }` and `- { Title, Entry Point, steps }` parse equivalently. Lower-snake-case alternates `title` and `entry-point` are also accepted for the field names.

### Step grammar

Each step is a string of the form `<src> → <dst>` or `<src> →[<kind>] <dst>` (Unicode arrow `→`). Default kind is `calls`. Steps carry types in the `calls` / `event` / `consumes` family — the runtime-flow types. Structural types (`enabled-by`, `hosted-by`, `available-through`) belong in the standalone `connectors:` block.

### Compiled output

Each connector emitted from a scenario step carries `scenario`, `sequence`, and `step` metadata. `step` is the index within its sequence (resets per sequence), so `(scenario, sequence, step)` uniquely locates the connector.

```yaml
- from: business-user
  to:   chat-surface
  type: calls
  source: scenario-step
  scenario: conversational
  sequence: user-initiated-conversation-with-ai-agent
  step: 0
```

## Standalone connectors — three entry shapes

The source `connectors:` block carries typed standalone edges. The compiler accepts:

```yaml
connectors:
  # Object form — fully explicit; required for non-default types or extra metadata
  - { from: A, to: B, type: enabled-by }
  - { from: A, to: B, type: hosted-by }
  - { from: A, to: B, type: available-through }
  - { from: A, to: B, type: consumes }
  - { from: A, to: B, type: event }

  # Pair form — shorthand for type: calls
  - [A, B]

  # Natural-language form — verb phrase determines the type
  - business-agent is enabled by agent-orchestrator
  - business-agent is hosted by agent-orchestrator
  - legacy-application is available through legacy-tool-bridge
  - business-agent calls knowledge-index
  - workflow-engine consumes app-database
  - platform-api emits to command-bus
```

Endpoints accept any reference: a global component id, an actor name, a block name, or a location id.

### Natural-language verb table

| Phrase | Connector type |
|---|---|
| `<X> is enabled by <Y>` | `enabled-by` |
| `<X> is hosted by <Y>` | `hosted-by` |
| `<X> is available through <Y>` | `available-through` |
| `<X> calls <Y>` / `<X> invokes <Y>` | `calls` |
| `<X> consumes <Y>` | `consumes` |
| `<X> emits to <Y>` / `<X> publishes to <Y>` / `<X> sends event to <Y>` | `event` |

Subject and object are whitespace-delimited tokens; direction is `from = subject, to = object` regardless of voice. The original string is preserved as `natural:` on the resolved connector for traceability. Unparseable strings are rejected with an error.

## Reference syntax

References everywhere are bare global ids — actors, blocks, locations, and components share a single namespace.

| Form | Resolves to |
|---|---|
| `<id>` matching an actor | The named actor. |
| `<id>` matching a block | The named block. |
| `<id>` matching a location | The named location (valid as `to:` for `hosted-by` / `enabled-by`). |
| `<id>` matching a component | The named component. |

The `<location>:<id>` qualified form is **not supported** — the compiler errors on it.

## Path conventions for icons

- **Inside a library's `index.yaml`:** paths starting with `resources/` are **library-relative** (resolve under `technology_library/<lib>/resources/`).
- **In an architecture file or cross-library reference:** paths are **project-root-relative** (`technology_library/microsoft/resources/<file>`, `ai_ea/resources/<file>`).

## Icon resolution chain

When the renderer needs an icon for a component, it resolves four levels:

1. Component-specific icon (component declares its own `icon:`)
2. Technology icon (from the first `implemented-by` technology)
3. Category icon (from the component's `category`)
4. Lettered fallback (initial of the component label)
